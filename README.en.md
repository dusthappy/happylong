# happlylong

**An AI-agent-driven workbench for personal multi-project product development** — manage `Requirement → PRD → Development → Smoke Test` across multiple independent projects with one lightweight pipeline. Real codebases are mounted via symlinks, leaving their original structure untouched.

## What is this

happlylong (**hy** for short) turns "a product-dev process with a PRD gate" into a set of AI-agent Skills plus a single-file CLI that runs inside your existing editor/terminal:

- **No PRD, no code changes**: every change to a business repo must first go through `/hy-req`, which closes the PRD and its acceptance criteria (AC) — only then may the agent touch code;
- **Session-scoped iteration isolation**: each agent session binds independently to one iteration through a stable ID, so multiple agents and windows can develop different workspaces in parallel; a new unbound session must explicitly choose an existing or new iteration before execution;
- **Automatic multi-repo orchestration**: split frontend/backend repos, shared backend mounted by multiple projects — `/hy-dev` orders and routes repos by role automatically;
- **Traceable iterations**: every iteration writes four flat files (prd / contract / plan / smoke) under `workspace/{project}/iterations/{id}/` — auditable end to end.

## Design principles

| Principle | Meaning |
|-----------|---------|
| **Single-track, lightweight** | One pipeline `req → dev → test`; PRD and contract close within the req stage. No multi-framework, multi-mode machinery |
| **Zero platform mirroring** | Only `AGENTS.md` (the cross-platform open standard) and the `.hy/i18n/` bilingual language sources are maintained (`.agents/skills/` is an install artifact); no .cursor/.claude mirror directories or sync mechanisms |
| **The CLI is the source of truth** | A single-file CLI, `happlylong.py`, manages skeletons, symlinks, iterations, sessions, health checks, and language; all state lives in YAML files — no hidden database |
| **Three-stage state machine** | An iteration has exactly `prd → dev → smoke` plus a contract-closure field; artifacts are four flat files |

## Quick start

Requirements: Python ≥ 3.10 + [PyYAML](requirements.txt) (the only runtime dependency); an AI IDE that supports `AGENTS.md` and `.agents/skills` (native in ZCode / Codex; Claude Code reads the root `CLAUDE.md` generated by `init` — link the skills yourself, see the FAQ).

**Command language (full i18n)**: the first `init` auto-detects your system locale (zh → Chinese, otherwise English) and pins it; switch anytime with `lang` — CLI messages, iteration/knowledge templates, skills and AGENTS.md all follow the same language. Sources live in `.hy/i18n/{zh,en}/`; `.agents/skills/` and the root `AGENTS.md`/`CLAUDE.md` are **local install artifacts** generated by `init`/`lang` (never committed) — run `init` right after cloning.

Clone the repository from GitHub's **Code** menu, then run:

```bash
cd happlylong
python3 -m pip install -r requirements.txt   # PyYAML, the only runtime dependency
python3 happlylong.py init          # skeleton self-check (idempotent; rebuilds the local registry workspace/_index.yaml) + install the language pack
python3 happlylong.py init --lang en  # or pick the command language explicitly (en/zh)
python3 happlylong.py lang            # show current language; python3 happlylong.py lang en to switch
python3 happlylong.py --session-id setup-check doctor  # health check (--fix auto-repairs what can be repaired)
```

Open this directory in your AI IDE and all `/hy-*` commands become available. **Start a requirement**:

```
/hy-req --project example --title "Sample requirement"   # create iteration + fill PRD + decide repository scope + contract routing
/hy-dev                                                  # contract fallback → plan → implement → self-check; multi-repo BE→FE chaining
/hy-test                                                  # smoke test; on fail, /hy-fix
/hy-knowledge iteration                                  # after all pass, distill this change into the knowledge base
```

> Explicit `/hy-req --title` is the “new PRD” signal: whether or not the session is already bound, it creates and binds a new iteration. Without `--title`, routing starts from the current session; if unbound, the agent asks whether to bind an existing iteration or create a new one.

**Cross-agent session protocol**: a leading `--session-id` has the highest priority, followed by `HY_SESSION_ID`; Codex sessions can also be identified automatically through `CODEX_THREAD_ID`. Each binding is written atomically to `.hy/session/bindings/{hash}.yaml`. Only a SHA-256 digest under a fixed namespace is stored; the raw ID is never persisted. Every active or previous binding explicitly stores `project`, `iteration_id`, and `iteration_path`, and the path must exactly equal `workspace/{project}/iterations/{iteration_id}`. Both reads and writes validate this invariant; a workspace is never guessed from a bare iteration ID, recency, or cwd. Other agents should inject a stable, unique `HY_SESSION_ID` into the **session launch environment**:

```bash
export HY_SESSION_ID="claude:project-a:conversation-001"  # unique per session; unchanged for its lifetime
python3 happlylong.py session show
# If the environment cannot be configured, pass the same value before every subcommand:
python3 happlylong.py --session-id "claude:project-a:conversation-001" session show
```

The PowerShell equivalent is `$env:HY_SESSION_ID = "claude:project-a:conversation-001"`.

Context compaction does not alter the on-disk binding. As long as the ID remains unchanged across compaction, an agent restart that preserves the environment, or an agent handoff, it resolves to the same iteration. For a cross-agent handoff of one logical session, explicitly use the same `HY_SESSION_ID` on both sides and keep only one active writer at a time; genuinely concurrent sessions must use different IDs. Without a trustworthy ID, binding-dependent commands **fail closed** instead of falling back to a shared `current.yaml`, preventing silent cross-wiring.

**Unbound-session entry gate**: when a new session first receives a `/hy-*` command or natural-language request that would advance requirements, development, fixing, rechecking, smoke testing, or iteration distillation, it checks the binding first. The entire stdout of `session show` is one YAML document. When unbound, it returns `active: false` plus a machine-readable `entry_gate` that declares the workspace root and required binding fields. The agent then lists valid iterations and enters an Ask-First loop in which you choose either an existing iteration or a new one. Invalid input produces no artifacts or code changes; the agent asks again. Once binding or creation succeeds, it resumes the original request. The sole exception is explicit `/hy-req --title`, which unambiguously means a new PRD and creates a new iteration as soon as the project is resolved. Pure Q&A, framework navigation/spec/role review, project or symlink onboarding, diagnostics, framework-source maintenance and open-source/release preparation, and `/hy-knowledge bootstrap` are exempt from the business-iteration gate.

**Onboarding a project with an existing codebase**: initialize its knowledge base first (injected directly from code, cold start with zero iterations):

```
/hy-knowledge bootstrap --project example
```

## Skills (all hy- prefixed)

| Command | Purpose |
|---------|---------|
| `/hy-spec` | Meta-spec: P0/P1 constraints + execution lifecycle + output quality grades |
| `/hy-guide` | Framework map, pipeline navigation, scenario-based quick reference |
| `/hy-roles` | PM / architect / developer three-perspective review (review only, no writes) |
| `/hy-req` | One-stop iteration + PRD entry (single-file PRD + AC + repository-scope decision + contract branching) |
| `/hy-dev` | Four-stage dev state machine (contract fallback → plan → implement → self-check) + multi-repo chaining |
| `/hy-fix` | Systematic defect fixing (fix-*.md trail) |
| `/hy-review` | Independent code review (review.md verdict) |
| `/hy-test` | Smoke execution (AC↔result↔evidence table; fail flows back to /hy-fix) |
| `/hy-knowledge` | Knowledge-base bootstrap cold start + iteration change distillation |
| `/hy-project` | Project registration, three symlink modes, pending links, doctor check |

## shared: cross-project standards

`shared/` ships with the framework and holds cross-project standards (general coding/Git, TypeScript/Go/Rust language standards, security rules, testing standards), pointed to by `.hy/config.yaml → paths.shared_rules` and verified by `doctor`.

## workspace: your business-project area (local only, never committed)

`workspace/` is your personal business area. **The entire directory is excluded by `.gitignore` and never enters the public repo** — the project registry and each project's profile/knowledge/iterations live only on your machine; the fictional sample is at [examples/example/](examples/example/).

Register a project first (real project dirs live on your machine, isolated from the public repo):

```bash
python3 happlylong.py project new myapp --title "My App"
# single repo
python3 happlylong.py link add myapp myapp /abs/path/myapp --role fullstack
# frontend + backend repos
python3 happlylong.py link add myapp myapp_fe /abs/path/myapp_fe --role frontend
python3 happlylong.py link add myapp myapp_be /abs/path/myapp_be --role backend
# shared backend + subproject (multiple projects mount one backend repo, routed by backend_apps submodules)
python3 happlylong.py link add myapp shared_be /abs/path/shared_be --role backend --shared \
  --app myapp=api/myapp,internal/biz/myapp,internal/service/myapp,internal/data/myapp,sql/myapp
# target dir not created yet: register first, link later
python3 happlylong.py link add myapp myapp_new /abs/path/myapp_new --role frontend --pending
python3 happlylong.py link apply myapp          # one-shot linking once the dir exists
```

Full details: the `/hy-project` Skill and the sample at [examples/example/](examples/example/).

## FAQ

- **Why no .cursor/.claude mirror directories?** `AGENTS.md` is the cross-platform open standard (`init` also generates a root `CLAUDE.md` containing just an `@AGENTS.md` reference, recognized by Claude Code directly); ZCode/Codex read `.agents/` natively. The framework maintains no sync mechanism.
- **How do I get the `/hy-*` skills in Claude Code?** No platform mirrors are maintained; link the skills once yourself: `mkdir -p .claude && ln -s ../.agents/skills .claude/skills` (run from the repo root; Claude Code's project skill path is `.claude/skills/`).
- **Why is there no workspace/ in the repo?** `workspace/` is the local business area (real projects, registry, iteration artifacts) and is **never committed as a whole**; framework-level shared standards live in root `shared/`, and the fictional sample in `examples/`.
- **How do I avoid breaking other projects when changing a shared backend repo?** Shared repos are routed to subproject directories per `backend_apps.{name}.paths`; `/hy-dev` routes automatically, and cross-subproject changes are a scope checkpoint that pauses for confirmation.
- **When does an iteration close?** After `/hy-test` reports all pass, you commit the business code, then run `python3 happlylong.py iter close` (requires smoke=pass).
- **Can concurrent AI sessions get cross-wired?** Codex isolates them automatically through `CODEX_THREAD_ID`; every other agent must give each session a stable, unique `HY_SESSION_ID` (or consistently pass the same `--session-id`). Without a trustworthy ID, the command fails instead of sharing `current.yaml`. `session show/set/back/clear`, `iter new`, and binding-dependent `iter show/close` operate only on the current session; show/close bypass session-based resolution when both `--project` and `--iteration-id` are explicit.
- **What happens if a new unbound session starts with “continue development”?** The agent lists valid iterations and asks whether to bind an existing one or create a new one, repeating until the target is valid or you cancel. It never guesses the “latest” iteration. `/hy-req --title "..."` is different: it explicitly means a new PRD and creates a new iteration directly.
- **How do I migrate the legacy `.hy/session/current.yaml`?** It is never read automatically. First configure a stable ID for the current agent, then use the old file's `project` and `iteration_id` values with `python3 happlylong.py session set {project} {iteration_id}`. Keep the old file only for manual reference.
- **How is privacy protected in the public repo?** See [.hy/opensource.md](.hy/opensource.md): a three-layer isolation model plus a pre-release scan checklist (the real project-name pattern source is a local private file, never committed).
